# Contributing to LightEvent

Any level of contribution is welcome, and we want it to be easy to engage with the development of the project. Contributions come in all shapes and sizes, from one-line documentation fixes to major features or bugfixes. If you're new to web software or open source, this is a great project to start with because it applies almost all of the most common practices in web development.

## Versioning

This project follows [Semver](https://semver.org/). Generally speaking, we will avoid breaking changes whenever possible. You can find release notes on the [Releases](https://github.com/aarongodin/lightevent/releases) page.

## Issues

The [issues](https://github.com/aarongodin/lightevent/issues) section of GitHub is for bug tracking and feature requests.

### Bugs

When submitting a bug report, please follow the issue template and fill it out. It makes it much easier for the maintainers to understand the issue at hand. Critical bugs will be addressed as soon as possible, but there are no guarantees for turnaround time. Minor issues will usually be rolled into a new version when it's appropriate to release the next version.

## Developer Guide

### Prerequisites

* [Go 1.26 or newer](https://go.dev/) (the `toolchain` line in `go.mod` downloads the exact version automatically)
* [Node.js 22.22 or newer](https://nodejs.org/en)

Code generators (`buf`, `sqlc`, `protoc-gen-go`, `protoc-gen-connect-go`) are pinned in `tools/go.mod` and run through `go tool`, so nothing else needs to be installed globally. `make help` lists every task.

### Project setup

```sh
make install                 # Go modules and npm packages (npm workspaces)
cp .envrc-example .envrc     # then load it, e.g. with direnv
make build-admin             # build the admin UI that the server embeds
make start                   # run the server on http://localhost:8080
```

The server reads its configuration from environment variables; `.envrc-example` has sensible values for local development, including `BOOTSTRAP_USERNAME`/`BOOTSTRAP_PASSWORD`, which create the first user on an empty database, and `EMAIL_PROVIDER=log`, which prints emails (such as member verification codes) to the server log. [direnv](https://direnv.net/) is a convenient way to load it.

There is also an [air](https://github.com/air-verse/air) config in the project. Running `air` rebuilds and restarts the server when Go, SQL or template files change.

### Admin UI development

The admin UI (`admin/`) is a React app built with Vite. For live reloading, run the Go server and the Vite dev server side by side:

```sh
make start       # terminal 1
make dev-admin   # terminal 2, then open http://localhost:5500
```

The dev server proxies `/rpc`, `/login` and `/auth` to the Go server. The login page is rendered by the server from `internal/access/static/login.html.tmpl`; its CSS is generated by `npm -w admin run build:login-css` (included in `make build-admin`). `pm2 start` runs the admin dev server and a watcher for the login CSS together (see `ecosystem.config.js`).

### Client app development

The client app (`client/`) is a [Preact](https://preactjs.com) app that websites embed with a single script; see [docs/client.md](./docs/client.md). It is built into `client/dist/lightevent-client.js`, which the server embeds and serves at `/client/lightevent-client.js`. For development, run the playground page next to the Go server:

```sh
make start        # terminal 1, with CLIENT_ALLOWED_ORIGINS=http://localhost:5600 (in .envrc-example)
make dev-client   # terminal 2, then open http://localhost:5600
```

The playground calls the server at `VITE_LIGHTEVENT_URL` (default `http://localhost:8080`) from another origin, like a real website does. `make build-client` builds the bundle and fails when it grows past its 100 KB budget. The client calls the API with plain `fetch` and imports only the generated JSON types from `client/src/gen`, so no protobuf runtime ends up in the bundle; keep it that way.

### Generated code

* The API is defined in `proto/lightevent/v1/service.proto`. Go and TypeScript code is generated with [buf](https://buf.build) into `internal/gen`, `admin/src/gen` and `client/src/gen`.
* Database access is generated by [sqlc](https://sqlc.dev) from `db/queries/*.sql` into `internal/storage`.
* The schema lives in `db/migrations`. Migrations are applied automatically when the server starts.

Run `make generate` after changing any of these, and commit the generated files.

### Checks

```sh
make lint    # go vet, gofmt, buf lint, Biome, TypeScript
make test    # Go unit tests (with the race detector)
make format  # gofmt and Biome formatting
```

### Browser tests

The admin UI and client app are tested end to end with [Playwright](https://playwright.dev/) in `e2e/`:

```sh
npx -w e2e playwright install chromium   # once, downloads the browser
make test-e2e                             # or: npm -w e2e test
npm -w e2e run test:ui                    # Playwright's interactive UI mode
```

The tests build the admin UI, client app and server, then start a server on port 18080 with a fresh database in `e2e/.tmp/` (see `e2e/scripts/server.mjs`). Client app tests embed the app in a page served from another origin, `http://localhost:18081` (see `e2e/scripts/host.mjs`), like a real website. Each run signs in once as the bootstrap admin and reuses that session. Tests run in parallel against the same server, so each test creates its own data with unique names, mostly through the JSON API (`Api` in `e2e/tests/fixtures.ts`), and uses the browser for the behavior under test. Emails are sent through the `log` provider and can be read in tests with `emailsTo()`.

Useful environment variables: `E2E_SKIP_ADMIN_BUILD=1` and `E2E_SKIP_CLIENT_BUILD=1` skip rebuilding the admin UI and client app, `E2E_PORT` changes the port, and `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` uses an existing Chromium instead of the downloaded one. Failure screenshots and traces are written to `e2e/.tmp/test-results/` (`npx -w e2e playwright show-trace <trace.zip>`).

TypeScript and JSON are formatted and linted with [Biome](https://biomejs.dev); `biome.json` at the repository root is the single source of configuration.

### Building a release binary

```sh
make build   # admin UI + client app + bin/lightevent
```

The binary is statically linked (`CGO_ENABLED=0`) because SQLite is provided by the pure-Go `modernc.org/sqlite` driver, so it cross-compiles with `GOOS`/`GOARCH` like any other Go program. Timezone data is embedded as well.

### Using the API

The API is served with [Connect](https://connectrpc.com) under `/rpc`. Every RPC is a `POST` to `/rpc/lightevent.v1.LightEventService/<Method>` and accepts either protobuf or JSON. Access to each RPC is declared in `internal/access/policy.go`.

The simplest way to call the API is with an API key, created in the admin UI under Settings → API keys:

```
~ curl -s http://localhost:8080/rpc/lightevent.v1.LightEventService/Ping \
    -H 'Content-Type: application/json' \
    -H "Authorization: Bearer $LIGHTEVENT_API_KEY" \
    -d '{}'
{"subjectUid":"…","scheme":"api-key","displayName":"my key"}
```

Without credentials, RPCs that require authentication return `401` with `{"code":"unauthenticated"}`. Browser requests from other origins that change state are rejected (CSRF protection), except API requests from the websites allowed to embed the client app, which receive CORS headers and authenticate members with bearer tokens instead of cookies.


## Pull Requests

When you have a change to propose, follow the standard pull request workflow by forking this repo, pushing to a branch in your fork, and opening a PR in this repo using your fork and branch as the source.

Please fill out the information in the default PR description as it makes it easier to scan and understand what has changed, as well as ensure that criteria for making a change have been met. If you can link to relevant issues this helps with pruning any issues the PR resolves.
